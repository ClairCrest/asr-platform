# ASR Platform: Build Plan

English-only speech-to-text inference platform.
Go control plane, Python inference workers, TypeScript dashboard, Docker, Kubernetes.

Repo name suggestion: `asr-platform` (rename freely).
Owner: github.com/ClairCrest

---

## 0. Purpose and non-goals

### What this project is
A self-hosted transcription service. A user uploads an audio file, the system queues it,
a worker pool transcribes it with a pretrained English Whisper model, and a dashboard shows
live job status and the finished transcript with timestamps.

### What it must demonstrate
| Signal | Where it shows up |
|---|---|
| Backend engineering | Go API with layered architecture, real error handling |
| Distributed systems | queue, leases, retries, dead letter, idempotency |
| Frontend | TypeScript dashboard with live updates over WebSocket |
| Ops | multi-stage Docker builds, K8s manifests, probes, autoscaling, metrics |
| ML awareness | model selection, batching, real-time-factor measurement, cost per audio hour |

### Explicit non-goals
- No model fine-tuning. Inference only, using a pretrained English model.
- No Thai or multilingual support. English audio only, and the system says so clearly.
- No speaker diarization in v1. Note it as future work.
- No billing, no teams or orgs. Single-user accounts only.
- Not a SaaS. This is a portfolio artifact, so polish the README over adding features.

## 1. Decisions already made

Flip any of these before phase 0 starts, not halfway through.

| Area | Choice | Reason |
|---|---|---|
| API language | Go 1.23+ | core requirement of the project |
| Router | `chi/v5` | thin, stdlib-compatible, good middleware story |
| DB | PostgreSQL 16 | job state, users, transcripts |
| DB access | `pgx/v5` + `sqlc` | typed queries, no ORM magic to explain away |
| Migrations | `golang-migrate` | plain SQL files, readable in the repo |
| Queue | Redis Streams + consumer groups | at-least-once with acks, no extra broker to run |
| Object storage | MinIO (S3 API) | swaps to real S3 with an env var change |
| Realtime | `coder/websocket` | maintained, context-aware |
| Worker language | Python 3.11 | uses existing ML skill, `faster-whisper` is the fastest path |
| Model | `faster-whisper` `small.en` (int8) | English-only, CPU-viable, ~2x real time on 4 cores |
| Frontend | Vite + React 18 + TypeScript | fast, containerizes to a static nginx image |
| Frontend data | TanStack Query + native WebSocket | cache and invalidation without hand-rolling |
| Styling | Tailwind | speed |
| Auth | JWT access token + API key for programmatic use | passwords hashed with argon2id |
| Logging | `log/slog`, JSON output | K8s-friendly |
| Metrics | `prometheus/client_golang` | phase 5 |
| K8s target | `kind` locally, Kustomize overlays for cloud | cheap to iterate, portable later |

## 2. Architecture

```
                        ┌──────────────────────────┐
                        │  web  (React + TS)       │
                        │  nginx static container  │
                        └───────────┬──────────────┘
                          REST      │      WebSocket
                                    ▼
                        ┌──────────────────────────┐
                        │  api  (Go)               │
                        │  - auth, uploads, jobs   │
                        │  - WS hub                │
                        │  - reaper goroutine      │
                        └──┬───────────┬────────┬──┘
                           │           │        │
              ┌────────────▼──┐  ┌─────▼────┐  ┌▼──────────────┐
              │  PostgreSQL   │  │  MinIO   │  │ Redis Streams │
              │  job state    │  │  audio + │  │ jobs:pending  │
              │  transcripts  │  │  outputs │  │ group=workers │
              └───────────────┘  └─────┬────┘  └───┬───────────┘
                                       │           │
                                  ┌────▼───────────▼────┐
                                  │  worker  (Python)   │
                                  │  faster-whisper     │
                                  │  N replicas, scaled │
                                  │  on stream backlog  │
                                  └─────────────────────┘
```

### Why the split
The Go side never loads a model. It owns state, delivery guarantees, and the API contract.
The Python side is stateless and disposable: pull a message, download audio, transcribe,
write result, ack. That separation is the whole point of the design and belongs in the README.

## 3. Data model

All tables use `uuid` primary keys generated by the application, not the database.

```sql
-- users
id             uuid primary key
email          text not null unique
password_hash  text not null
created_at     timestamptz not null default now()

-- api_keys
id            uuid primary key
user_id       uuid not null references users(id) on delete cascade
name          text not null
key_hash      text not null unique          -- sha256 of the raw key
last_used_at  timestamptz
created_at    timestamptz not null default now()
revoked_at    timestamptz

-- jobs
id                 uuid primary key
user_id            uuid not null references users(id) on delete cascade
status             text not null            -- see state machine below
idempotency_key    text                     -- unique per (user_id, idempotency_key)
object_key         text not null            -- MinIO path of the source audio
original_filename  text not null
size_bytes         bigint not null
duration_seconds   double precision         -- filled in by the worker
model              text not null default 'small.en'
attempts           int  not null default 0
max_attempts       int  not null default 3
error_code         text                     -- machine readable
error_message      text
worker_id          text
lease_expires_at   timestamptz
created_at         timestamptz not null default now()
started_at         timestamptz
finished_at        timestamptz

-- transcripts
id                    uuid primary key
job_id                uuid not null unique references jobs(id) on delete cascade
text                  text not null
language_detected     text not null
language_probability  double precision not null
model                 text not null
processing_seconds    double precision not null
real_time_factor      double precision not null   -- processing / audio duration
created_at            timestamptz not null default now()

-- segments
id             uuid primary key
transcript_id  uuid not null references transcripts(id) on delete cascade
idx            int not null
start_ms       int not null
end_ms         int not null
text           text not null
avg_logprob    double precision
-- unique (transcript_id, idx)

-- job_events   (append only, drives the WebSocket feed and the audit trail)
id          uuid primary key
job_id      uuid not null references jobs(id) on delete cascade
event_type  text not null   -- created, queued, leased, progress, succeeded, failed, retrying, cancelled
payload     jsonb not null default '{}'
created_at  timestamptz not null default now()
```

Indexes to create: `jobs(user_id, created_at desc)`, `jobs(status)`,
`jobs(status, lease_expires_at)` for the reaper, `job_events(job_id, created_at)`.

### Job state machine

```
  pending ──► queued ──► processing ──► succeeded
                 ▲            │
                 │            ├──► failed        (attempts >= max_attempts)
                 └────────────┤
                  retrying    └──► cancelled     (user request)
```

Rules:
- Only `queued` and `processing` jobs are cancellable.
- Only `failed` jobs are retryable, and a retry resets `attempts` to 0 and returns to `queued`.
- A `processing` job whose `lease_expires_at` has passed is reclaimed by the reaper:
  increment `attempts`, then either requeue as `retrying` or terminate as `failed`.
- Every transition writes a `job_events` row. No exceptions. The WebSocket hub reads from there.

## 4. API surface

Base path `/api/v1`. JSON only. Errors follow one shape:

```json
{ "error": { "code": "job_not_found", "message": "human readable", "request_id": "..." } }
```

| Method | Path | Notes |
|---|---|---|
| POST | `/auth/register` | email + password, returns tokens |
| POST | `/auth/login` | returns access token (15 min) and refresh token (7 days) |
| POST | `/auth/refresh` | |
| GET | `/me` | current user |
| POST | `/api-keys` | returns the raw key exactly once |
| GET | `/api-keys` | list, never returns the raw key |
| DELETE | `/api-keys/{id}` | revoke |
| POST | `/uploads` | body: filename, size_bytes, content_type. Returns presigned PUT URL + object_key |
| POST | `/jobs` | body: object_key, original_filename, model. Honours `Idempotency-Key` header |
| GET | `/jobs` | filters: status, cursor, limit. Keyset pagination, not offset |
| GET | `/jobs/{id}` | includes latest events |
| POST | `/jobs/{id}/cancel` | |
| POST | `/jobs/{id}/retry` | |
| DELETE | `/jobs/{id}` | soft delete, also removes the audio object |
| GET | `/jobs/{id}/transcript` | `?format=json\|txt\|srt\|vtt` |
| GET | `/ws` | WebSocket, authenticated by short-lived ticket from `POST /ws-ticket` |
| GET | `/healthz` | liveness, no dependency checks |
| GET | `/readyz` | readiness, pings Postgres + Redis + MinIO |
| GET | `/metrics` | Prometheus, phase 5, separate port 9090 |

### Upload constraints, enforced server side
- Max 200 MB, max 2 hours of audio.
- Accepted: `audio/wav`, `audio/mpeg`, `audio/mp4`, `audio/x-m4a`, `audio/flac`, `audio/ogg`.
- The worker rejects anything ffmpeg cannot decode and fails the job with `error_code=unsupported_media`.

### English-only handling
The model is `.en`, so it always decodes as English. The worker still records
`language_detected` and `language_probability` from a detection pass on the first 30 seconds.
If probability for English is below 0.5, the job still succeeds but sets a
`language_warning` flag in the transcript payload, and the UI shows a banner saying the audio
does not appear to be English and the transcript may be unreliable. Do not silently pretend.

## 6. Build phases

Work strictly in order. Each phase ends with a merged PR and a git tag.
Do not start the next phase until the acceptance criteria pass.

### Phase 0: Skeleton (2 to 3 days)
- Init repo, Go module, Python project, Vite app.
- `docker-compose.yml` bringing up Postgres, Redis, MinIO with healthchecks.
- Migrations 001 through 006 covering the full schema in section 3.
- Makefile targets: `up`, `down`, `migrate-up`, `migrate-down`, `sqlc`, `test`, `lint`.
- `.env.example` with every variable the services read.

**Acceptance**: `make up && make migrate-up` on a clean machine produces all tables.
Tag `v0.1.0`.

### Phase 1: Go API core (1 week)
- Config loading, structured logging, request ID middleware, panic recovery.
- Auth: register, login, refresh, argon2id, JWT middleware, API keys.
- Uploads: presigned PUT generation against MinIO.
- Jobs: create with idempotency, get, list with keyset pagination, cancel, retry, delete.
- Enqueue to Redis Stream on create.
- `/healthz` and `/readyz`.
- Table-driven tests on the job state machine. Integration tests with testcontainers.

**Acceptance**: a shell script uploads a file, creates a job, and reads it back as `queued`.
Coverage on `internal/job` above 70 percent. Tag `v0.2.0`.

### Phase 2: Python worker (1 week)
- Consumer loop: `XREADGROUP` with a consumer group, block 5s, claim one message.
- Download audio from MinIO, probe with ffmpeg, normalize to 16 kHz mono.
- Transcribe with `faster-whisper` `small.en`, int8 on CPU.
- Write transcript, segments, and events. Ack the message. Renew the lease periodically
  during long files so the reaper does not steal a job that is still progressing.
- Failure paths: unsupported media, decode error, model crash, OOM. Each maps to an `error_code`.
- Reaper goroutine in the Go API: scan for expired leases, requeue or fail.

**Acceptance**: submit a 60 second English WAV, poll until `succeeded`, transcript text is
non-empty and roughly correct. Kill a worker mid-job and confirm the reaper requeues it.
Tag `v0.3.0`.

### Phase 3: Dashboard (1 week)
- Login and register screens, token storage and refresh.
- Upload with drag and drop, client-side size and type validation, progress bar on the presigned PUT.
- Jobs table: status badges, duration, model, relative timestamps, filters.
- WebSocket hook that subscribes to the user's job events and patches the TanStack Query cache.
  Reconnect with backoff. Fall back to polling every 5 seconds if the socket is down.
- Job detail: transcript viewer with clickable segment timestamps synced to an audio player,
  copy button, and download as txt, srt, vtt.
- API keys page.
- Empty states, error states, loading skeletons. This is what makes it look finished.

**Acceptance**: the entire flow from upload to reading a transcript works with no manual API calls,
and status changes appear without a page refresh. Tag `v0.4.0`.

### Phase 4: Containers and Kubernetes (4 to 5 days)
- Multi-stage Dockerfiles. Go image on distroless or `scratch`, non-root user, under 30 MB.
  Worker image bakes the model weights in at build time. Web image builds then serves via nginx.
- Kustomize base: Deployments for api, worker, web. StatefulSets for Postgres and MinIO.
  ConfigMap for non-secrets, Secret for credentials. Services, Ingress.
- Liveness and readiness probes wired to the real endpoints. Resource requests and limits on every container.
- Migration Job that runs before the API rolls out, using an init container or a Helm-style pre-hook.
- `kind-cluster.yaml` plus a `make kind-up` that builds images, loads them into kind, and applies the overlay.

**Acceptance**: `make kind-up` gives a working platform at `http://localhost:8080` from a cold start.
Deleting a worker pod does not lose a job. Tag `v0.5.0`.

### Phase 5: Scale and observability (4 to 5 days)
- Prometheus metrics on the API: `jobs_submitted_total`, `jobs_completed_total{status}`,
  `job_queue_depth`, `job_duration_seconds` histogram, `audio_seconds_processed_total`.
- Worker exports `worker_rtf` and `worker_busy`.
- KEDA `ScaledObject` on Redis Stream pending count, min 1 max 8 replicas. Include a plain
  CPU-based HPA in the cloud overlay as a fallback for clusters without KEDA.
- Prometheus and Grafana in the local overlay, with one dashboard JSON committed to the repo.
- k6 load test: 50 concurrent submissions, record queue drain time and p95 latency.
- `docs/benchmarks.md` with RTF per model size and estimated cost per audio hour versus
  Google Speech-to-Text and AWS Transcribe. You did this comparison at Botnoi, so it is
  familiar ground and it makes the project read like engineering rather than a demo.

**Acceptance**: a burst of 50 jobs visibly scales the worker Deployment up and back down.
Screenshot the Grafana panel for the README. Tag `v1.0.0`.

### Phase 6: Presentation (2 to 3 days)
This phase is not optional. Most reviewers spend 90 seconds on the repo.
- README: one-paragraph description, architecture diagram as an image, animated GIF of the
  upload-to-transcript flow, quickstart in three commands, tech table, what it does not do.
- `docs/architecture.md` explaining the queue guarantees and why the control plane is separate.
- Three or four ADRs: why Redis Streams over NATS, why Python workers, why presigned uploads,
  why keyset pagination.
- Pin the repo on the GitHub profile.

## 8. Working agreement for Claude Code

Read this section before writing any code.

1. **One phase at a time.** Do not jump ahead. Stop at the end of each phase and report
   what passes and what does not.
2. **Conventional Commits**, small and frequent. `feat(api): add job cancellation endpoint`.
   Never a single commit containing an entire phase.
3. **Branch per phase**, PR into `main`, tag on merge. Solo development still deserves history.
4. **Ask before adding a dependency** that is not listed in section 1.
5. **Tests go in with the code**, not in a cleanup pass at the end.
6. **No secrets in the repo.** Everything through env vars, with `.env.example` kept in sync.
7. **Errors are values.** Wrap with `fmt.Errorf("...: %w", err)`, define sentinel errors in the
   service layer, and map them to HTTP codes in exactly one place.
8. **The state machine lives in `internal/job`.** No handler mutates job status directly.
9. When a design question comes up that this plan does not answer, write an ADR in `docs/adr/`
   rather than deciding silently.
